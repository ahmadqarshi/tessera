# @tessera/api

NestJS REST API for Tessera. Serves both portals, holds the two backend signing keys, brokers
KYC/AML providers, issues on-chain claims, executes privileged agent operations, and serves
indexer-backed reads. See [`CLAUDE.md`](./CLAUDE.md) for the module map and hard rules.

## Database

Postgres, accessed through Prisma. **The schema is the single source of truth for the whole
monorepo**: the indexer (`apps/indexer`) imports the client generated from this workspace — there
is no second schema.

- **Schema:** [`prisma/schema.prisma`](./prisma/schema.prisma)
- **Generated client:** `@prisma/client` (regenerated by `db:generate` / `postinstall`)
- **Connection string:** `DATABASE_URL` (see `.env` / `.env.example`); the docker-compose default
  is `postgresql://rwa:rwa@localhost:5432/rwa?schema=public`
- **Data-model reference:** [`../../docs/api/DATA-MODEL.md`](../../docs/api/DATA-MODEL.md) —
  a table per model plus the table-ownership map

Columns are **snake_case** in Postgres while the TypeScript model fields stay **camelCase** (each
field carries an `@map`, each model an `@@map`). This keeps raw SQL — `$queryRaw`, the operations
runbook, the Phase 3 reconcile command — free of the double-quoting that unmapped camelCase columns
would otherwise force. Every address column stores the **lowercase** 0x-hex form; every amount is
`Decimal(78,0)` (exact uint256 base units), never a float. Table ownership is **single-writer**: the API owns the
identity/offering/auth/audit tables, the indexer owns the chain-derived tables, and `claims` /
`claim_chain_state` are a deliberate split joined at read time via `effectiveClaimStatus()` from
`@tessera/shared`. The rationale lives in the schema and in the data-model doc.

### Running migrations

Bring Postgres up first, then apply migrations. All commands are runnable from the repo root
(they filter to this workspace) or from `apps/api`.

```bash
docker compose -f infra/docker-compose.yml up -d   # postgres + anvil

pnpm db:migrate           # create/apply a dev migration (prisma migrate dev)
pnpm db:migrate:deploy    # apply committed migrations, no prompts (CI / prod)
pnpm db:generate          # regenerate the Prisma client after a schema change
```

Migrations are committed under [`prisma/migrations/`](./prisma/migrations/); `db:migrate:deploy`
never edits the schema and is the path used in CI and on Amoy.

### Resetting

`db:reset` **drops and recreates** the database, replays every migration, and runs the seed. It
is destructive — local development only.

```bash
pnpm db:reset             # prisma migrate reset --force
```

### Inspecting

```bash
pnpm db:studio            # Prisma Studio — browse tables in the browser
```
